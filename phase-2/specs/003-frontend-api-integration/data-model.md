# Data Model: Frontend Application & Secure API Integration

**Feature**: 003-frontend-api-integration
**Date**: 2026-02-09
**Source**: Backend API from Spec 002

## Overview

This document defines the TypeScript interfaces used by the frontend to interact with the backend Task API. These types mirror the backend schemas from Spec 002.

## Entities

### Task

The primary entity representing a todo item.

```typescript
interface Task {
  id: string;           // UUID assigned by backend
  title: string;        // Required, 1-200 characters
  description: string | null;  // Optional, max 1000 characters
  completed: boolean;   // Default: false
  user_id: string;      // Owner's user ID from JWT
  created_at: string;   // ISO 8601 timestamp
  updated_at: string;   // ISO 8601 timestamp
}
```

**Constraints**:
- `id`: Generated by backend, UUID format
- `title`: Required, non-empty, max 200 characters
- `description`: Optional, max 1000 characters
- `completed`: Boolean, defaults to false
- `user_id`: Must match authenticated user's ID
- Timestamps: UTC, ISO 8601 format

### TaskCreate

Request body for creating a new task.

```typescript
interface TaskCreate {
  title: string;        // Required, 1-200 characters
  description?: string; // Optional, max 1000 characters
}
```

**Validation**:
- `title`: Required, must not be empty, max 200 chars
- `description`: Optional, max 1000 chars if provided

### TaskUpdate

Request body for updating an existing task.

```typescript
interface TaskUpdate {
  title?: string;       // Optional, 1-200 characters if provided
  description?: string; // Optional, max 1000 characters
}
```

**Validation**:
- At least one field must be provided
- `title`: If provided, must not be empty, max 200 chars
- `description`: If provided, max 1000 chars

### User Context

User information from Better Auth session.

```typescript
interface User {
  id: string;           // User UUID

}

interface Session {
  token: string;        // JWT token for API requests
  // Additional session fields from Better Auth

interface SessionData {
  user: User;

}
```

## API Response Types

### Single Task Response

Returned by GET, POST, PUT, PATCH endpoints.

```typescript
type TaskResponse = Task;
```

### Task List Response

Returned by GET list endpoint.

```typescript
type TaskListResponse = Task[];
```

**Ordering**: Tasks are returned in descending order by `created_at` (newest first).

### Error Response

Returned for 4xx and 5xx status codes.

```typescript
interface ErrorResponse {
  detail: string;  // Human-readable error message
}
```

**Common Error Details**:
- `"Authorization header required"` - 401, no token
- `"Invalid or expired token"` - 401, bad token
- `"Access denied"` - 403, user_id mismatch
- `"Task not found"` - 404, invalid task_id
- `"Title is required"` - 400, validation error

## Relationships

```
User (1) ----< (*) Task
```

- One user can have many tasks
- Each task belongs to exactly one user
- User can only access their own tasks (enforced by backend)

## Data Flow

### Read Flow

```
Dashboard Mount
      ↓
useSession() → user_id, token
      ↓
useTasks(userId, token) → fetch tasks
      ↓
API: GET /api/v1/users/{user_id}/tasks
      ↓
Response: Task[]
      ↓
State: tasks = response.data
```

### Write Flow (Create)

```
User fills form
      ↓
Validate: title required
      ↓
API: POST /api/v1/users/{user_id}/tasks
     Body: { title, description }
      ↓
Response: Task (created)
      ↓
State: tasks = [newTask, ...tasks]
```

### Update Flow

```
User edits task
      ↓
Validate: title not empty (if provided)
      ↓
API: PUT /api/v1/users/{user_id}/tasks/{task_id}
     Body: { title?, description? }
      ↓
Response: Task (updated)
      ↓
State: tasks = tasks.map(t => t.id === id ? updatedTask : t)
```

### Toggle Flow (Optimistic)

```
User clicks toggle
      ↓
State: task.completed = !task.completed (optimistic)
      ↓
API: PATCH /api/v1/users/{user_id}/tasks/{task_id}/complete
      ↓
Success: confirm state
Error: revert state, show error
```

### Delete Flow

```
User clicks delete → confirm dialog
      ↓
User confirms
      ↓
API: DELETE /api/v1/users/{user_id}/tasks/{task_id}
      ↓
Response: 204 No Content
      ↓
State: tasks = tasks.filter(t => t.id !== id)
```

## Validation Rules (Frontend)

| Field | Rule | Error Message |
|-------|------|---------------|
| title | Required | "Title is required" |
| title | Max 200 chars | "Title must be 200 characters or less" |
| title | Non-empty | "Title cannot be empty" |
| description | Max 1000 chars | "Description must be 1000 characters or less" |

**Note**: Backend performs the same validations. Frontend validation improves UX by catching errors before API call.
